# A RATCHET, BOTH DIRECTIONS, same rule as known_failures.txt: a new entry
# means somebody just wrote a method nobody calls, and an entry that leaves
# must be deleted in the same commit that wires it.

# THE SHARED-NAME BLIND SPOT, NOW MEASURED AND PARTLY CLOSED.
# The identifier sweep cannot tell whose method a name refers to, so
# `_candidate_methods` drops any name two classes both define. That was an
# honest lower bound and a far looser one than it read: 60 public method names
# in bot/ are multiply defined, covering 274 methods nothing checked.
# ComplianceEngine.format_for_telegram is the worked example — no caller
# anywhere, never listed here, because seven classes define that name.
#
# A second pass now attributes a call `<recv>.<name>()` by resolving the
# receiver through `self.x = Foo()` and `x = Foo()`, and reports a class no
# call site resolves to. It is SOUND rather than complete: one unresolvable
# receiver makes the whole name ambiguous, because the alternative is guessing.
# **31** method names remain ambiguous and are not checked by anything — the
# number is pinned by test_the_ambiguity_the_sweep_cannot_resolve_is_stated,
# so it cannot rot into a claim.
#
# 33 -> 31 when alert_manager, performance_tracker and feedback_loop were
# deleted: fewer classes in the tree means fewer shared method names the sweep
# has to give up on. The four METHOD entries those modules owned went with
# them, and the stale-entry half of the ratchet is what refused to pass until
# they did.
#
# It was 34 until `observe` left the list, and how it left is worth recording
# because it looks like the ratchet loosening and is the opposite. Two classes
# define `observe` — PersonPeak and CatalogWatch — and both are genuinely
# called (person_peak.py:158, market_scanner.py:295); the name was ambiguous,
# not unreachable, so nothing was ever being checked about either. Adding
# # SignalTracker.record_outcome — RECORDED, and the reason is a live defect it
# already caused rather than a plan to wire it. Signals are recorded
# (`record_signal` is called); outcomes never are, so `closed` is permanently
# empty in the running bot. `_pair_stats_locked` computed
# `len(wins)/len(closed) if closed else 0.0`, so /signals rendered every pair
# as 0 wins, 0 losses, an all-hollow win-rate bar and 0.0% — a measured record
# of failure assembled from the absence of one, which is the shape CLAUDE.md
# names. That display is fixed (win_rate is None over zero closes and the card
# prints an em dash); the FEED is not, and joining a signal id to its closing
# trade is a real piece of work, not a wiring line.
#

# `engine.signal_tracker`, and the engine has no such attribute — the tracker
# lives on TelegramHandler. `getattr(..., None)` means /api/signals answers an
# empty list forever rather than erroring, so nothing ever reported it.
