# Generated and enforced by tests/test_no_new_unreachable_modules.py. Each of
# these has passing tests and no production caller, which means those tests say
# nothing about whether the module runs — the state `token_dossier`,
# `presale_claims` and `deployer_history` were in until they were wired.
#
# This is a RATCHET, not a permission slip. A new entry appearing means somebody
# just built another scorer nobody calls. Removing one — because you wired it —
# must happen in the same commit, or test_the_baseline_has_no_stale_entries
# fails, same rule as known_failures.txt.
#
# Not all of these are equally wrong, which is why they are recorded rather than
# guessed at. Sorted by how uncomfortable they are to find here.

# authority_preflight LEFT this list, and the note that used to sit here was
# right in a way it did not know. It said "a runner that reported CONFIRMED from
# no probe would be worse than no runner". That was not a hypothetical about
# some future wiring — it was a description of the code as written.
# probe_posture opened with
#
#     "environment":          "demo" if sandbox else "live",
#     "expected_environment": "demo" if sandbox else "live",
#
# both sides of the comparison from the same argument, both set BEFORE the probe
# ran. The environment dimension could never report VIOLATION and reported
# CONFIRMED ("key is a live key, matching the bot") off a probe that had failed
# outright. test_environment_mismatch_is_violation proved the VIOLATION branch
# worked the whole time; no PRODUCER could reach it. Green test, unreachable
# branch — the #999 shape one level in, and invisible to any source scan,
# because the code was not just present, it was correct.
#
# The product decision the old note deferred: posture is checked at
# CREDENTIAL-LINK time, in /connect. That is the moment a user hands over a key,
# and the question worth asking then is the one nothing in this repo asked —
# not "can this key read" (three probes already answer that) and not "is it the
# right environment" (validate_bitget_credentials already diagnoses 40099 with
# far better messages), but CAN THIS KEY MOVE THE MONEY OUT. Bitget answers it
# on a read-only endpoint; no withdrawal is ever attempted.
#
# The vocabulary that decides it was transcribed from docs and never confirmed
# against a live key, so bitget_withdraw_scope only answers "off" when it
# recognises EVERY authority in the response. A wrong or stale vocabulary then
# degrades to "unknown" — the status quo — instead of reading a response it
# cannot parse as proof of non-custody.
#
# validation_gate LEFT this list. Its own docstring carried the accusation —
# "the engine does not consult this gate before executing trades" — and it
# could not simply be consulted: storage was in-memory so every restart emptied
# it, nothing called record_validation so it was empty anyway, and
# is_validated() answered False for a strategy nobody had ever tested. Those
# three make fail-closed a halt at every redeploy and fail-open a decorative
# gate. It persists now, bot/backtest/runner.py records into it (never from
# SYNTHETIC data), the verdict is three-valued, and the risk gate consults it
# as a tighten-only fail-open hook beside intent_policy and the authority
# envelope — default OFF, and shadow before enforce.

# ── bot/learning: NOT here any more, and the reason matters ────────────────
# Ten bot/learning modules sat under this heading reading "an entire subsystem
# with no caller". They were never unreachable. bot/core/engine.py:354
# constructs LearningOrchestrator() on every run, and the orchestrator imports
# all ten as `from .experience import ...` — a relative import the detector
# recorded as a module literally named ".experience", matching nothing.
#
# The detector's own docstring warned that a checker with a blind spot
# manufactures the accusation it exists to prevent. It then did exactly that,
# to ten modules, in the file carrying the warning. Fixed, and pinned by
# test_relative_imports_count_as_reachability.
